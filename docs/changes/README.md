# 改动记录（给 ci 审阅用）

> **谁写**：programmer。每个执行单元或每个会话收尾时更新，**未落盘视为未完成**。
> **谁读**：ci 在发布前逐条对照 `git diff` 审阅；用户手测时可据此逐项验收。
> **放哪**：待发布批次写在 `docs/changes/next.md`；ci 发布后把整份文件改名为 `docs/changes/vX.Y.Z.md` 归档，并新建空的 `next.md`。
> **原则**：这里写“用户看得见的变化 + 契约与风险 + 验证证据”，不写实现流水账；CHANGELOG 从这里取“用户可读”部分，细节仍以 `git diff` 为准。

## 一条改动的最小信息

每条都要有：

1. **结果**：用户能看到/感觉到什么（一句话，不带实现词）。
2. **入口**：哪个页面/按钮/接口；文件 + 关键函数或行号。
3. **原因**：修 bug 要写根因（为什么原来会坏），新功能写用户要求。
4. **契约**：有没有动路由、事件名、存储键、locale 结构、`shelves.json`/`索引.json`、`package.json` 的 `exports`/`engines`/`dsh`。动了要写“加了什么、是否向后兼容、谁确认的”。
5. **验证**：命令 + 退出码 + 覆盖了哪条验收；没覆盖的写清楚。
6. **风险**：边界、迁移、旧数据、并发、失败恢复；没有就写“无”。

## 模板

```markdown
## T-YYYYMMDD-NN · <一句话结果>

- 入口：<页面 / 按钮 / 路由>（<文件>:<行>）
- 原因：<根因或用户要求>
- 契约：无 / 新增 <接口>（向后兼容）/ 改动 <契约>（已确认）
- 验证：`<命令>` → 退出码 0；<测试文件> N 条
- 风险：<边界/迁移/未覆盖>
- 用户可见：<CHANGELOG 用的一句话>
```
