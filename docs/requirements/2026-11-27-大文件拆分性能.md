## 1. 背景与目标

拆书是插件的主路径：整本 PDF → 拆分面板（每行 4 页缩略图 + 页间剪刀）→ 按页切成章节。文件很大时（用户实际书库里有 900 页以上的整本），打开拆分面板很慢、滚动很卡，并有闪退（WebView 崩溃）风险。目标是让大文件也能安全拆分，不牺牲小文件的现有手感。

## 2. 现状证据（代码级，2026-11-27 只读核对）

- `client.js` `SplitDialog` 在打开时**一次性渲染每页一个缩略图格**：`Array.from({ length: count }, ...)`，每格一个 `<canvas>` 和一个剪刀按钮；946 页的书就是 946 个格子 + 946 个 canvas 节点。这是打开慢与首屏卡顿的直接来源。
- 缩略图绘制是按需的（`IntersectionObserver` → `paintSplitThumb`），但**画过就不再释放**：绘制后 `node.dataset.painted = '1'` 并 `observer.unobserve(node)`，格子离开视口后位图仍然保留。
- 单张缩略图的位图不小：`paintSplitThumb` 取 CSS 宽度上限 760px × `devicePixelRatio`（上限 2），即约 1520 × 2000+ 设备像素、每张 10 MB 量级；把一本 900 页的书从头滚到尾，累计位图可达 GB 级，足以让 WebView 被系统杀掉（闪退）。
- 页码跳转（2026-11-27 已加：拆分结果那行的页码可点击滚动并短暂高亮）已经存在，可以作为超大文件的浏览方式，但面板本身仍会为全部页建格子。
- 尚未在本环境复现真实崩溃（无浏览器可跑）；以上为代码证据 + 用户报告，**排期前需按第 6 节复现**。

## 4. 验收标准（目标值待用户拍板）

用用户书库里 946 页的整本 PDF（`整本\Abstract Algebra…`，约 35 MB）作为大文件样本，210 页的 Asymptotic 作为小文件对照：

1. 打开拆分面板后，**首屏可操作时间** ≤ T1 秒（建议 T1 = 3 s，待拍板）。
2. 从顶部拖滚动条到底部再回顶部，**不白屏、不卡死、不崩溃**；缩略图在视口内 ≤ T2 ms 出现（建议 T2 = 400 ms，待拍板）。
3. 连续快速滚动/拖拽 3 分钟，**不发生闪退**；任务管理器里该 WebView 的内存峰值 ≤ M（建议 M = 800 MB，待拍板）。
4. 简略模式下：滚动与点剪刀操作流畅，切点、范围、预览与小文件一致，能完成一次真实拆分。
5. 小文件（210 页）：打开时间与滚动流畅度相对当前版本**不劣化**（允许 ±10% 误差）。
6. 拆分结果（文件数、命名、范围）与小文件路径逐项一致，拆分完成后书架出现「未按命名拆分」的书（本轮已有的归类行为）。

## 5. 范围与不做

- 只做**拆分面板**的加载与渲染性能；不重做拆分算法，不改变拆分产物的命名规则。
- 不改动已有的页码跳转、切点记忆（`pdfdesk:split-cuts:<书id>`）、拆分完成后的两个选择。
- 不在本轮解决 pdf.js 打开 35 MB 本体的耗时（`getDocument` 阶段单独测量后另议）。
- 不做后台拆分队列/服务端拆分。

## 7. 建议方向（参考，不是已批准方案）

- **虚拟化缩略图网格**：按行只渲染视口 ± 若干行，空白处用与页高等高的占位撑起滚动条；页码跳转与切点仍按页号工作。
- **位图 LRU / 释放**：只保留视口附近 N 张 canvas 位图，离开即缩成 1×1 或清空；回来重画。
- **限制分辨率**：缩略图宽度与 DPR 设上限（清晰度与内存取平衡）。
- **批量绘制**：每帧最多画一张、用 `requestIdleCallback` 排队，滚动时取消。
- **简略模式**：超大文件默认不画缩略图，保留页码、剪刀、页码跳转；提供开关。
- **打开前置**：先统计页数并给出「共 N 页」骨架，再逐步补齐缩略图。

## 9. 风险

- 虚拟化后 `attach` 节点 Map、页码跳转、剪刀定位、切点高亮都依赖真实 DOM，需要一起改；改不好会破坏现有拆分流程（属受保护交互）。
- 如果只做 LRU 不做虚拟化，946 个 DOM/Canvas 节点仍在，打开慢的问题解决不了。
- 「简略模式」若默认开启，会改变现有用户（你）的操作习惯，需要明确开关位置与默认值。

## 10. 2026-11-27 复测与方案（programmer 提案，待拍板）

> 用户追问：「现在拆分工具，载入又要载入半天，我看 WPS 的效果几乎都是瞬间完成的呀？参考一下如何去加速，给个方案出来」。
> 本节先给实测与根因，再给两档方案；未改代码。

### 10.1 实测（本机，2026-11-27）

| 样本 | 页数 | 大小 | pdf.js 解析（Node legacy，冷） | pdf.js 首页内容解析 | PyMuPDF 打开 | PyMuPDF 缩略图 |
| --- | --- | --- | --- | --- | --- | --- |
| 数学分析 第五版（下册） | 340 | 86.7 MB | 868 ms | 182 ms | **3 ms** | 1–18 ms/页（139×202） |
| 数学分析 第五版（上册） | 322 | 75.6 MB | 76 ms（热缓存） | 167 ms | — | — |
| 近世代数基础 | 196 | 7.8 MB | 71 ms | 132 ms | — | — |

结论：**PDF 解析不是「半天」的主因**（大样本冷启动 < 1 s，热缓存 < 100 ms）；PyMuPDF 更是 3 ms 打开、毫秒级出缩略图。时间花在拆分面板的 UI 与重复工作上。

### 10.2 代码级根因（按影响排序）

1. **每次打开都重新解析，且不复用共享缓存**：`SplitDialog` 自己 `lib.getDocument(...)`（`client.js:6096`），而阅读器/右栏已经有 `sharedDocuments`（`client.js:3331`、`:3413`）。读者先打开过同一本书，拆面板仍从零解析。
2. **关闭不销毁**：加载完只把 `alive=false`（`client.js:6104`），`getDocument` 的 task/document 没有 `destroy()`；反复开关会累积已解析文档与 worker 缓存，越开越慢、内存越高。
3. **一次性建 946 个格子**：`Array.from({ length: count })`（`client.js:6246`）为每页建 `div + canvas + span + 剪刀按钮`（约 6–7 个节点/页），大书一次 6000+ 节点、近千 canvas。
4. **画完才定尺寸，整表反复重排**：canvas 初始 300×150，`paintSplitThumb` 之后才设真实宽高（`client.js:5767`），`.md-split-page` 没有预留纵横比（`client.js:18382–18384`）。每画一张，格高变化，946 项网格重新布局，滚动时持续抖动。
5. **每个格子带阴影**：946 个 `box-shadow` 在滚动容器里合成，放大掉帧。
6. **位图不释放**：画过就 `dataset.painted='1'` 并 `unobserve`（`client.js:6136–6138`），离开视口仍占内存；DPR 上限 2（`client.js:5767`）。

### 10.3 为什么 WPS 是「瞬间」

WPS 用原生 PDF 引擎 + 内存映射打开文件，只光栅化可见页；缩略图由原生代码生成并缓存，滚动时按需取用，DOM 里没有「一页一个画布」。浏览器里的 pdf.js 是 JS 解析 + canvas，天然慢一档，但可以通过「不重复解析 + 只渲染可见行 + Host 生成并缓存缩略图」把体感拉回同一量级。

### 10.4 方案 A：前端止血（1 轮，无新路由，推荐先做）

1. `SplitDialog` 改用 `sharedDocuments.claim(url, ...)`，复用阅读器已解析的文档；关闭时 `release()`，无引用时 `destroy()`。
2. 给 `.md-split-page` 预留纵横比（首页 viewport 或默认 0.7），画完不再改格高；去掉每格阴影，只保留 hover/选中描边。
3. 分批挂载：首屏先挂 32–40 页，其余用 `requestAnimationFrame`/`requestIdleCallback` 分块补；或先上 `content-visibility: auto` + `contain-intrinsic-size`。
4. 绘制队列：同一时刻只画 1–2 张；快速滚动时暂停，停稳再补。
5. 离屏释放：canvas 离开视口 ±2 屏就 `width=height=1`，回来重画；拆面板 DPR 上限降到 1.5。
6. 目标：大书首次打开 ≤ 1.5 s、二次打开 ≤ 500 ms、滚动明显顺滑；改动集中在 `client.js`，不动路由/存储。

### 10.5 方案 B：WPS 式 Host 缩略图（1–2 轮，需批准新路由）

1. 新增只读路由（same-origin，按当前书库解析书，禁止路径穿越）：
   - `GET /pdfdesk/pdf-info?book=&code=` → `{ pages, aspect }`（PyMuPDF `fitz.open` + `page_count` + 首页 `rect`，实测 3 ms）；
   - `GET /pdfdesk/pdf-thumb?book=&code=&page=&w=200` → WebP/JPEG（实测 1–18 ms/页），带 `ETag`/`Cache-Control: immutable`。
2. 缩略图缓存：`.pdfdesk/thumbs/<书>@<mtime>@<w>/p<NNN>.webp`（或按文件 etag 分目录）；首次按需生成可见页，后台低优先级补齐其余页；删书/换版本自动失效。
3. 拆面板彻底移除 pdf.js：页数/纵横比来自 `pdf-info`，网格用 `<img loading="lazy">` + 行级虚拟化；不再建 canvas，不再解析 86 MB 文件。按页剪刀、页码范围、输出预览、`/pdfdesk/split` 全部不变。
4. 降级：Python/PyMuPDF 不可用时回到现有 pdf.js 路径（方案 A 的实现），或显示「简略模式」。
5. 目标：大书首次打开 ≤ 500 ms（1 个 info + 约 8 张可见图，并发 4）、二次打开 ≤ 200 ms；滚动只加载新行；内存不再随页数增长。
6. 契约：新增两条 `/pdfdesk/*` 只读路由 + `.pdfdesk/thumbs/` 缓存目录；需要你确认后才能动（AGENTS 受保护契约）。

### 10.6 方案 C：可选增强

- 打开整本卡时在空闲时预热 `pdf-info` / 首屏缩略图。
- 批量 sprite（一次请求一整屏 4×3 张），减少请求数。
- 后台预生成整本缩略图（340 页约 1–2 s，946 页约 3–5 s），下次打开全命中。
- 阅读器侧改用同一套 `sharedDocuments` 预热，切换阅读/拆分不重复解析。

## 10.8 实施记录（2026-11-27，已按方案 B 落地）

用户选择方案 B，批准新增路由与缓存。已实现：

- Host：`POST /pdfdesk/pdf-layout`（页数/页面尺寸 + 渲染一个范围）、`GET /pdfdesk/pdf-thumb`（缓存 JPEG、ETag）；缓存位于 `~/.dsh/pdfdesk/thumbs/<路径+大小+mtime 的 sha1>/`，不入书库、不进备份；渲染工具 `tools/pdf_thumbs.py`（PyMuPDF + Pillow，JPEG q80，240 px）。
- 客户端：`SplitDialog` 改为 Host 优先，首屏 1–12 页，滚动按 ≤60 页一批补；每页 `<img loading="lazy">` + 预留 `aspect-ratio`，Host 模式不建 canvas、不解析 PDF；pdf.js 路径保留为无 Python/PyMuPDF 时的降级。
- 实测：86.7 MB / 340 页样本，首 12 页 434 ms（含 Python 启动），缓存命中 24 页 257 ms，约 9.7 KB/页；PyMuPDF 打开 3 ms。
- 验证：新增 `split-thumbs-route-test.mjs`（注入假渲染器）与 `split-thumbs-client-test.mjs`；全部 split/host 回归与 `check-*` 通过。本会话 Node 不能 spawn（EPERM），真实 Python 渲染分支未进自动化，脚本已单独用 `py` 跑过。
- **未做**：行级虚拟化与离屏图片卸载（内存随浏览页数增长）、缓存自动清理、持久 Python 渲染进程（首次仍有约 0.4 s 启动）。若真机大书从头滚到尾仍卡，下一轮做这几项。
