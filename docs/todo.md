## 入队规则

一个单元必须满足：

- **一件事**：一个会话可以完成，且只有一个用户可感知的结果。
- **有边界**：写明涉及的文件/模块；预计超过 2 个文件时，执行前必须另出计划等确认。
- **有验收来源**：只能引用 `docs/requirements/` 的具体小节或 `AGENTS.md` 的硬约束，不能写“看起来正常”。
- **有依赖**：前置单元、环境、数据或用户确认写清楚；依赖未满足不标为可执行。
- **不打包**：不把“顺便修一下”“顺手重构”塞进同一单元；同类但独立的修复拆成独立单元。
- **不重复拆解**：同一个结果被拆成多个会话反复规划时，boss 必须退回原因，不再继续切碎。

## 状态与报告

| 状态 | 含义 | 谁写入 |
| --- | --- | --- |
| `待执行` | 已拆好，等待承接角色 | boss |
| `进行中` | 当前会话正在做 | programmer |
| `待审查` | programmer 已完成，等 code-reviewer | programmer |
| `待测试` | 审查无 Critical，等 tester | code-reviewer |
| `待发布` | 测试通过，等用户明确发布指令 | tester |
| `退回执行` | 审查有 Critical 或测试不通过，回到 programmer | code-reviewer / tester |
| `阻塞` | 缺依赖/需要用户确认；必须写明阻塞原因 | 当前环节角色 |
| `完成` | **已发布**（版本与发布记录另见 `CHANGELOG.md` / Release） | release-manager |
| `已关闭` | 用户确认无需修复/取消，或现象不再出现；**不等于发布** | boss |

状态只能按 `待执行 → 进行中 → 待审查 → 待测试 → 待发布 → 完成` 前进；审查有 Critical 或测试不通过用 `退回执行`。boss 可把无需修复/取消的单元置 `已关闭`（终态，与发布无关）。当前环节角色只改状态列和报告列，不改执行单元、验收来源、影响范围、依赖。boss 负责新增、拆解、优先级、验收来源和关闭（放弃/取消），不负责追每次交接。

报告规则：审查结论只由 code-reviewer 写 `docs/reviews/<单元ID>.md`，测试结论只由 tester 写 `docs/tests/<单元ID>.md`；每轮追加 `## Round N`，不覆盖历史；“报告”列填这两份文件路径。programmer 完成时只置 `待审查`，不预填报告路径。

## 优先级

- `P1`：明确的用户可见缺陷或已承诺的功能。
- `P2`：体验优化、文档补齐、非阻断清理。
