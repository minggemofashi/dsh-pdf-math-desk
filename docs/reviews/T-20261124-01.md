1. **`client.js:15882–15886`、`client.js:3415–3417`、`client.js:11608–11612`** — reader 未挂载时，右栏的“翻译中”没有完成感知；长期 running 的陈旧任务也无法区分，可能永久禁用。
   - **证据**：右栏只在 `translation.known === false` 时触发一次 refresh；`refreshTranslationFacts` 对 `status === 'running'` 只写 `translating: true` 并提前返回，不探测文件、不安排复查（`:3407–3417`）。任务完成/失败只由“仍挂载的 reader”（resume watcher 每 2 s，`:11608–11612`）或发起 `runTranslate` 的 reader 写事实并广播；reader 卸载后 `!mine()` 的分支直接 return（`:11610`），右栏不会收到完成。harness 只验证“reader 不在、job running 时保持禁用”（`.dsh-scratch/u1-test.mjs:578–588`），没有覆盖“任务随后完成”。另外，Host 崩溃/重启后 job 文件可能残留 `status: running`：reader 在时每 2 s 轮询且永不停止，右栏则永久禁用（`:3415–3417`）。
   - **影响**：只开右栏 tab 的用户在“任务已完成”或“任务已死”两种情况下，都可能看到“叠加”长期/永久禁用。前者违背“翻译完成即恢复”的验收 2 语义，也是用户 W3 “reader 是否挂载不得改变右栏叠加可用性”的动态边界；后者与 W2 的“锁死”同类，只是触发条件从 404 变成长期 running。主验收路径（重启后右栏恢复、无在途任务）不受影响。
   - **修复方向**：在右栏/共享缓存对 `translating === true` 或 `known === false` 加**有界**复查（单章单定时器、固定上限，或右栏 tab 可见时触发），完成/失败时写共享 facts 并广播；对长期 running 任务按 `startedAt`/进度做陈旧判定，或提供“重新检测”动作。programmer 在 `.dsh-scratch/u1-repro-evidence.md:175–187` 称用户已接受“reader 关闭后在途完成不主动推送”，但该接受只在仓库外证据，按 `AGENTS.md` §3 不属项目记忆；若接受，须由 boss 写入 `docs/todo.md` 或 `docs/decisions.md`，否则按待修复处理。

2. **`client.js:3436–3447`** — HEAD 探测只把 404 当“不存在”、2xx 当“存在”，304/5xx/403 或网络失败都留在“未知”；且 `fetch` 无超时、同一右栏挂载内不重试。
   - **证据**：`response.status === 404` → `exists = false`，`response.ok`（仅 2xx）→ `true`，其余（含 304）保持 `null` 后直接 return（`:3439–3446`）。PDF 路由带 ETag 且回 `private, max-age=0, must-revalidate`（`src/host/pdf-stream.js:27`、`:128–139`），命中浏览器缓存的 HEAD 有返回 304 的可能；此处的 `fetch` 没有像 `request()` 那样的超时/中止（对比 `client.js:2120–2163`），Host 卡住时 `facts.pending` 永不释放（`:3405`、`:3448–3452`）。SidePdfView 的 effect 依赖 `[bookId, code, translation.known]`（`:15886`），失败后同一挂载不会重跑。
   - **影响**：W3 的“未知不得永久禁用”实际只保证到“下次挂载/换章”；同一右栏 tab 内探测失败或 304 时会一直灰到重新挂载。programmer 的 R3 声称用户已批准该限制，同样只在仓库外证据（`.dsh-scratch/u1-repro-evidence.md:186`）。
   - **修复方向**：HEAD 显式 `cache: 'no-store'`（或把 `304` 视为存在），加与 `request` 一致的超时/中止；失败后做一次有界重试（或 tab 可见性触发），并加一条 harness/真机用例；若维持现状，由 boss 把该限制写入项目记忆。

3. **`client.js:3426–3432`、`client.js:11613–11627`、`client.js:11945–11960`** — W2 的清理逻辑对“任何 status 请求失败”都清 `pdfdesk:job:*`，不区分 404 与超时/5xx/网络错误；真实任务仍可能在 Host 侧继续跑。
   - **证据**：三处 `catch` 均 `forgetStoredJob` + 写 `translating: false`；`request()` 其实在 `error.code` 里区分了 `http-<status>`/服务端 code（`client.js:2140–2147`），代码没有使用。若 Host 暂时不可达或返回 5xx，正在运行任务的续看键会被删掉、UI 停止观察；任务随后完成时无人写 facts（右栏最多再 HEAD 一次、可能仍拿旧结果），用户看到“翻译失败”并可再次点“翻译本章”，存在并发启动同一章翻译的窗口。
   - **影响**：概率低但会造成任务上下文丢失/重复计费风险；W2 要求的 404 路径本身已正确。该条与用户“失败即复位/清理”的要求方向一致，属于实现粒度问题，不阻断本轮 tester。
   - **修复方向**：按 `error.code` 区分终态（`job-missing`/`http-404`、`bad-job`/`http-400`）与可重试错误（timeout、`http-5xx`、网络）；可重试错误保留 key 并重试一次，仍未恢复再清键；或经用户确认“任何失败都清键”后把该语义写清楚。
